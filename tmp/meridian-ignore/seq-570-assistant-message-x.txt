### 2. Where It Is Documented and Implemented

| Aspect | Documentation & Implementation | Details |
| :--- | :--- | :--- |
| **`MERIDIAN_BATCH_SPENT` error code** | [lessons-learned.md:407–423](<docs/lessons-learned.md#L407-L423>) (§3, §3.1) | Documented as *"Tool results were consumed, generation died before any reply."* Because Meridian consumes (`accept()`) the pending `tool_result` batch before streaming the model's response, retrying the identical request when the stream dies before `message_stop` would fail with HTTP `409` (`MERIDIAN_CONTINUATION_CONFLICT`: `already consumed`). |
| **Spent-batch classification & durability** | [spent-batch-plan.md:15–39](<docs/plugins/dsh-meridian-antigravity/spent-batch-plan.md#L15-L39>), [failure.js:43–73](<plugins/dsh-meridian-antigravity/lib/failure.js#L43-L73>), [errors.js:21–36](<plugins/dsh-meridian-antigravity/lib/errors.js#L21-L36>), [stream.js:130–135](<plugins/dsh-meridian-antigravity/lib/stream.js#L130-L135>) | When an SSE stream terminates or emits an in-band `error` event before `message_stop` on a request that carried a `tool_result` continuation, the connector classifies it as non-retryable `MERIDIAN_BATCH_SPENT` rather than retryable `TRANSPORT`. |
| **Underlying trigger (`Antigravity turn timed out`)** | [spent-batch-plan.md:113–120](<docs/plugins/dsh-meridian-antigravity/spent-batch-plan.md#L113-L120>) (§3) | Recorded in the Meridian ledger summary (`[504] x2 turn timed out`) alongside `503 UNAVAILABLE` ([lessons-learned.md:418–419](<docs/lessons-learned.md#L418-L419>)) and `502` content-filter blocks ([spent-batch-plan.md:20–25](<docs/plugins/dsh-meridian-antigravity/spent-batch-plan.md#L20-L25>)). |

### 3. Two Nuances Worth Noting from This Session

1. **Upstream cause in [lessons-learned.md:418–419](<docs/lessons-learned.md#L418-L419>):**
   - §3.1 of [lessons-learned.md:418–419](<docs/lessons-learned.md#L418-L419>) currently mentions only `UNAVAILABLE (code 503): No capacity available for model ... on the server` as the observed upstream cause of `MERIDIAN_BATCH_SPENT`.

2. **Recovery without forking:**
   - Although Turn 2 (`seq: 211`) and Turn 4 (`seq: 391`) ended with `turn/end` (`reason.kind: "error"`, `code: "MERIDIAN_BATCH_SPENT"`), sending a new user message in Turn 3 (`seq: 213–217`) succeeded cleanly because the new user message turned the next dispatch into a fresh user-message turn rather than a bare `tool_result` continuation.
   - You can recover `Review Unstaged Git Files` the same way: send a follow-up message asking the agent to write its review from the `git status` and `git log` results already in the transcript.
