### 1. [doctor.js](plugins/dsh-dd35-preset/doctor.js)

#### [doctor.js:6–18](plugins/dsh-dd35-preset/doctor.js#L6-L18) — Module documentation
* **Current:**
```javascript
 * Reports the campaign's *authoring debt*: places where the files disagree with
 * themselves or with what the table established. Every check here was chosen
 * because it is currently failing somewhere in a real campaign — the point is
 * to make silent gaps loud, not to enforce a schema.
 *
 * Two rules govern this module, and both are load-bearing:
 *
 *  1. **Read-only.** It never writes, ever. In particular it uses `loadState`,
 *     never `requireState`, because the latter *self-heals by creating*
 *     `state.json` — a write on what is supposed to be a read path.
 *  2. **It never throws.** A missing campaign, an unreadable directory, corrupt
 *     JSON: each is a *finding*, not an exception. A diagnostic that can crash
 *     the turn it was meant to help is worse than no diagnostic.
```
* **Proposed Replacement:**
```javascript
 * Reports campaign state inconsistencies: places where files disagree with
 * each other or deviate from established campaign data structures. Every check here
 * detects an inconsistency identified during campaign log analysis, identifying
 * unindexed entities, malformed files, or unreferenced stubs.
 *
 * Two operational invariants govern this module:
 *
 *  1. **Read-only.** It does not write to the filesystem. In particular it uses `loadState`,
 *     never `requireState`, because `requireState` creates `state.json` if absent,
 *     which alters campaign state during a diagnostic check.
 *  2. **It never throws.** A missing campaign, an unreadable directory, or corrupt
 *     JSON produces a diagnostic finding rather than throwing an unhandled exception.
```

### 2. [memory.js](plugins/dsh-dd35-preset/memory.js)

* **Current:**

#### [memory.js:52–63](plugins/dsh-dd35-preset/memory.js#L52-L63) — `rpcId` validation
* **Current:**
```javascript
/**
 * Genuine player input: a user-role message carrying the client-minted `rpcId`
 * that only the prompt path sets.
 *
 * The rpcId is the load-bearing part. `SessionCommandController.prompt()` mints
 * one from the request id for every prompt the Web client sends, while a
 * producer that injects model-facing content as a user-role message has none.
 * Keying on `kind === 'user'` alone was not enough: `dsh-context-pressure` used
 * exactly that kind for its pre-compaction notice, so the notice was captured as

 * `user` for a role reason.
```
* **Proposed Replacement:**
```javascript

 * Validates user-role input originating directly from the user prompt path via client-minted `rpcId`.
 *
 * `SessionCommandController.prompt()` assigns an `rpcId` derived from the request id
 * for client-submitted prompts. Automated plugins that inject messages with role `'user'`
 * do not include an `rpcId`. Filtering by `rpcId` prevents system notices (such as
 * compaction warnings) from being recorded as user input in turn transcripts.
```

```javascript
 *
 * Add a kind here when a new producer starts asking for work. Reporting kinds
```

* **Proposed Replacement:**

```javascript
 *

 * (`runtime-context`, `skill-catalog`, `tool-jobs`, `subagent-settled`) do not divert
 * dialogue flow, so the final assistant message remains the recorded response.
```

### 3. [context-index.js](plugins/dsh-dd35-preset/context-index.js)

#### [context-index.js:10–15](plugins/dsh-dd35-preset/context-index.js#L10-L15) — Deterministic matching architecture
* **Current:**
```javascript
 * This is deliberately not semantic search. Everything here is counting and
 * exact matching over files that already exist, so it costs nothing per turn and
 * every result can be traced back to the turn it came from. The semantic layer
 * stays deferred (§12.7): both providers configured in this profile are
 * external, so per-turn inference would be a recurring bill.
```
* **Proposed Replacement:**
```javascript
 * This implementation uses deterministic string and token matching over indexed transcripts

 * generation on the active turn path. Semantic search remains deferred (§12.7) to prevent
 * external API latency and token overhead during per-turn execution.
```

### 4. [state-store.js](plugins/dsh-dd35-preset/state-store.js)

#### [state-store.js:12–20](plugins/dsh-dd35-preset/state-store.js#L12-L20) — Data partitioning & workspace root
* **Current:**
```javascript
 * Division of truth (no field lives in two places):
 *   state.json   -> session facts: mode, clock, initiative order/index, scene, present entities
 *   entity sheet -> per-entity facts: hp, temp_hp, ac, conditions, resources, position, stats
 *
 * Every campaign path resolves against the *session's* workspace — the folder
 * the user opened, taken from `session.header.cwd` — and never against the
 * folder this bundle happens to live in. The root is bound per tool call and per
 * memory hook. An explicit `workspace` config pins it instead, for standalone
 * use and tests.
```
* **Proposed Replacement:**
```javascript
 * Data partitioning schema (non-overlapping fields):
 *   state.json   -> session-level state: mode, clock, initiative order/index, scene, present entities
 *   entity sheet -> entity-level state: hp, temp_hp, ac, conditions, resources, position, stats
 *
 * Campaign file paths resolve against the active session's workspace root (from
 * `session.header.cwd`) rather than the plugin installation directory.
 * The root is bound per tool invocation and memory hook, or specified explicitly via configuration for testing.
```

#### [state-store.js:58–61](plugins/dsh-dd35-preset/state-store.js#L58-L61) — Synchronous tool binding

* **Proposed Replacement:**

```javascript
 * Wraps tool execution to bind the active campaign and workspace root to the invoking session.
```

#### [state-store.js:164–169](plugins/dsh-dd35-preset/state-store.js#L164-L169) — Campaign directory membership

* **Proposed Replacement:**

#### [state-store.js:211–218](plugins/dsh-dd35-preset/state-store.js#L211-L218) — Session migration boundary
* **Current:**
```javascript

 * shipping this feature does not detach a campaign from a session already in
 * play. Every session created after it starts with **no campaign** and must be
 * bound by a choice the player made.
```

* **Proposed Replacement:**
```javascript

 * for backward compatibility. Sessions created after this timestamp initialize without

```

#### [state-store.js:304–313](plugins/dsh-dd35-preset/state-store.js#L304-L313) — Binding resolution order
* **Current:**
```javascript
 * The order matters and each rule earns its place:
 *
 *   `bound`     — the player chose, or `route_turn` pinned a legacy resolution.
 *   `inherited` — a fork with no entry of its own follows its parent.
 *   `legacy`    — created before {@link SESSION_BINDING_SINCE}, so the registry's
 *                 active campaign still governs it. This is the whole migration.
 *   `none`      — a session created since, unbound. A brand-new chat.
 *
 * Never throws: this runs on the prompt-assembly path, where a throw kills the
 * session before its first token.
```
* **Proposed Replacement:**
```javascript
 * Precedence hierarchy for session-to-campaign resolution:
 *
 *   `bound`     — explicit session binding or pinned legacy resolution.
 *   `inherited` — fork session inheriting binding from an ancestor session.
 *   `legacy`    — session predating {@link SESSION_BINDING_SINCE}, resolving via active registry.
 *   `none`      — unconfigured session created after {@link SESSION_BINDING_SINCE}.
 *
 * This function handles missing or malformed records without throwing exceptions,
 * ensuring prompt assembly completes during session initialization.
```
