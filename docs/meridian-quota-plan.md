# Meridian quota visibility and gating — implementation plan

Three things could be built from Meridian's quota data: stop wasting retries on quota failures, show
quota and activity in the composer, and prevent sending when quota is exhausted. The first two are
buildable. The third is not, and the research below says why.

Status: **plan only.** Every claim here was checked against your live Meridian instance or against
harness source; where something is an inference it is labelled as one.

## 1. What Meridian exposes

Meridian does publish quota, and it is a documented stable interface rather than an accident.
`/providers/status` is listed in its `api-contract.md` among the interfaces external plugins depend on,
with changes requiring owner approval, so it is a reasonable thing to build against.

Two endpoints carry the same data:

- `GET /providers/status` — per provider: `enabled`, `status`, `error`, `models`, `capabilities`,
  `activity`, and `accounts[]`. Each account has `windows[]` of `{ type, utilization, resetsAt }`, where
  `utilization` is a 0–1 fraction and `resetsAt` is an epoch millisecond timestamp.
- `GET /v1/usage/quota/all` — the same quota in a Claude-shaped envelope, `{ profiles: [...] }`.

Both read from the official `agy -p /usage --output-format json`. Gemini and Claude/GPT allowances are
kept separate and are never summed. Quota reads refresh in the background, so `/providers/status` can
return `status: loading` before the first reading lands.

There is also a reactive path. A quota failure maps to HTTP 429 or to an SSE error carrying retry
guidance, which is what you already saw in the compaction failure: *"Individual quota reached. Please
upgrade your subscription to increase your limits. Resets in 2h43m43s."* That string is generated by the
CLI and relayed by Meridian, not constructed by Meridian, which matters for how we detect it.

## 2. What your account actually returns today

I queried your service rather than trusting the documentation, and the answer changes the design.

```
provider status: unavailable
provider error : expected string at command.data.groups[1].buckets[1].reset_time, received undefined
account windows: []
activity       : {"requests":61,"errors":3,"inputTokens":581892,"outputTokens":31692,"cacheReadTokens":1960462}
```

So **there are no quota percentages to display for this account at all right now.** Meridian's own
schema rejects the `agy` usage report because one bucket has no `reset_time` field and the schema
requires one. That is a defect on Meridian's side, or a CLI format change it has not caught up with.
Updating Meridian and `agy` is the first thing to try; otherwise it belongs in a Meridian issue.

The `activity` block does work, and the numbers above are real: requests, errors, input and output
tokens, and cache reads for the last hour.

This is the single most important input to the plan. An indicator that silently shows nothing would
look broken and would be worse than no indicator, so "quota unavailable, here is why" has to be a
first-class state rather than an edge case.

## 3. How quota failures are handled today, and why that is wrong

There are two paths and both are currently retried, which wastes a round trip on a condition that
cannot succeed until a window resets.

| Path | Classified as | Retryable? |
| --- | --- | --- |
| HTTP 429 with a quota message | `QUOTA` | no |
| Quota error inside an SSE stream | `TRANSPORT` (via `streamInterrupted`) | **yes** |

The retryable set is declared in `lib/config.js`:

```js
retryableCodes: ['RATE_LIMIT', 'SERVER', 'TIMEOUT', 'TRANSPORT', 'EMPTY_RESPONSE', 'MERIDIAN_PENDING_REPLAYABLE']
```

That list is what this plan shipped against. It has since gained
`MERIDIAN_AGENT_INTERRUPTED` — Meridian's dropped-agent 502, split out of `SERVER` and retryable
exactly as `SERVER` was; see [`meridian-spent-batch-plan.md`](meridian-spent-batch-plan.md).

**Correction, found while implementing.** This section originally claimed that a quota 429 maps to
`RATE_LIMIT` and is retried. It does not. `errors.js:156` already classifies a 429 whose message matches
`QUOTA_HINTS` as `QUOTA` — the harness's own `QUOTA_EXCEEDED_CODE` (`llm/src/error.ts:28`), which is
absent from the retryable set — so that path was already correct and needed no new code.

The defect is only the second row. Your session log shows the quota text arriving mid-stream and being
reported as `Meridian Antigravity stream ended before message_stop (Individual quota reached… Resets in
2h43m43s.)`, which is `streamInterrupted` returning `TRANSPORT`, which the policy then retried twice. The
fix routes that case through the same `QUOTA` classification rather than inventing a code.

Neither path read the reset window out of the message, so `providerRetryAfterMs` now comes from it.

## 4. The composer, and what a plugin may do to it

`conversation.composer.bar` declares exactly the props you would want:

```ts
/** A feature-owned reason that makes message input inert while leaving model selection live. */
blocked?: { readonly reason: string }
/** Lock all message actions while preserving the resident composer surface. */
disabled?: boolean
```

Both are **owner** props. The owner is `ui-conversation`, the slot is `kind: single`, and it is already
occupied by the shipped composer with `replaceRisk: shadows-shipped-ui`. I searched the client packages
and the owner never sets either field, and no service exposes an equivalent. A plugin registering into
that slot is a registrant, not the owner, so it receives owner props rather than supplying them.

**A plugin therefore cannot prevent a send.** It would have to replace the shipped composer, which is
not a reasonable thing to do for a quota indicator.

What is available is rendering. These are list slots with `replaceRisk: none`:

- `conversation.composer.dock` — "ambient entries below the composer card", the natural home for a
  quota strip.
- `conversation.input.left` / `conversation.input.right` — compact controls in the composer tool row.
- `conversation.input.overlay` — floating entries inside the composer card.

Two mechanical notes for whichever we choose. The client half will need
`@deepseek-ai/dsh-client-ui-conversation` added to the `dsh.client.inject` list in `package.json`,
alongside the two entries already there, or the slot will not resolve. And in the current profile
`conversation.composer.bar` is a `session-maybe` slot, so the strip must render sensibly with no session.

## 5. Host to browser plumbing

The browser cannot read Meridian directly: the API key must stay server-side, and the page has no route
to the LAN service. The precedent in this repository is `plugins/dsh-tts`, which registers a host route
and hands the browser half a credential by injecting it into the served document:

```js
ctx.inject(['webServer'], (webCtx) => {
  webCtx.effect(() => webServer.register({ kind: 'prefix', path: prefix, handler }), '…-http-route')
  webCtx.effect(() => webServer.tapIndex((html) => {
    const identity = { prefix, token: setting(config.apiToken, '') }
    const tag = `<script>window.__DSH_TTS__=${JSON.stringify(identity).replace(/</g, '\\u003c')}</script>`
    return html.includes('</head>') ? html.replace('</head>', `${tag}</head>`) : tag + html
  }), '…-index-identity')
})
```

Plugin routes inherit none of the harness's own authentication, which is why the route authenticates
itself with that token. A rotated token needs a page refresh. The connector already has this shape of
`ctx.inject([...])` for the settings service, so the pattern fits without new machinery.

## 6. Work items, in order

### A. Classify quota failures distinctly

The only item that delivers value today, and the smallest.

- Add `MERIDIAN_QUOTA_EXHAUSTED`, deliberately absent from the default retryable set.
- Detect it on **both** paths: the non-2xx classifier in `lib/errors.js`, and the in-stream error path
  that currently funnels into `streamInterrupted`.
- Keep the matcher lenient and narrow, because the text is CLI-generated and may change: require a quota
  word plus a reached/exceeded/exhausted word, so an ordinary rate-limit 429 still classifies as
  `RATE_LIMIT` and keeps its retry.
- Parse the reset window when present (`Resets in 2h43m43s`) into milliseconds and attach it as
  `providerRetryAfterMs`, so the harness can report when the model becomes usable again. An unparseable
  window must yield "unknown", never zero.
- Tests: the matcher and the duration parser as pure functions, with the exact string from your session
  as a fixture, plus a case asserting that a plain rate-limit message is *not* caught.

### B. Read quota on the host

- A small client for `/providers/status`, reusing the connector's existing credential resolution and
  health-gate machinery rather than inventing a second path to Meridian.
- Normalize to a stable internal shape: `{ status, error, windows: [{ type, utilization, resetsAt }],
  activity, fetchedAt }`.
- Cache with a TTL and refresh in the background. A turn must never wait on quota: reading it is a
  convenience, not a precondition.
- **Pool the refresh behind one trigger.** Two sources call it — every assistant response, and a
  one-minute timer — and a single "last attempt" timestamp gates it, so whichever fires first satisfies
  the other. The effective cadence is at most one reading a minute.
- **That cadence is safe, and Meridian already bounds the cost.** There is no client-facing rate limit
  on the endpoint, and three layers sit behind it: `/providers/status` starts at most one background
  refresh per 10 seconds and only when none is in flight (`antigravityRuntime.ts:501`); the
  `agy -p /usage` call behind it runs at most once per 60 seconds on success, or 10 seconds after a
  failure (`:508`); and concurrent callers share one in-flight promise (`:509`). A one-minute poll is
  therefore at Meridian's own refresh rate rather than above it, and most reads return its cache instead
  of starting work. Polling faster would return identical numbers.
- **Serve our own cached copy from the route**, so browser refreshes, extra tabs and page loads do not
  each reach Meridian.
- The one thing to avoid is retrying through a CLI failure cooldown. `verifyAccount` can answer 503 with
  a retry-after while the account check cools down (`:526`), and Meridian surfaces that as an error on
  the cached reading rather than failing the request, so the strip should show it and wait rather than
  poll harder.
- Tests: the normalizer, with the `unavailable` payload from §2 as the primary fixture, since that is the
  real case today, alongside a healthy payload.

### C. Expose it to the browser half

- A prefix route plus `tapIndex` injection following §5, carrying `window.__DSH_MERIDIAN__`.
- The response is the normalized object from B. Bounded, and never containing the API key or any other
  credential.

### D. The composer strip

- Register into `conversation.composer.dock` and render three states honestly:
  - windows present: utilisation per window with a countdown to `resetsAt`;
  - no windows: "quota unavailable", with Meridian's own error, because that is the current truth;
  - request failed: the transport error, distinct from "Meridian cannot read quota".
- Show the activity numbers, which work today and are otherwise invisible.
- Poll on a slow interval, not per render or per keystroke.
- Theme tokens only, and no import of a Harness Client package, following the existing client half.

### E. Not doing: pre-send blocking

Recorded here so it is not re-litigated. The composer exposes no veto to a plugin, so the honest
fallback is A: the turn fails immediately with a message naming quota and the reset window, instead of
being retried twice and then failing with something that reads like a transport fault. That is not the
confirmation-dialog behaviour you asked about, and I would rather say so than ship something that looks
like a gate and is not one.

## 7. Risks

- **The strip will look broken if it does not handle `unavailable` well.** Today that is the only state
  your account can produce, so it is the state to design first rather than last.
- **The quota text is not ours.** It comes from the CLI through Meridian, so matching it is a guess that
  will eventually be wrong. Keep the matcher narrow, and never let a matcher failure convert a real
  failure into a silent success.
- **A non-retryable quota code could swallow a transient 429.** The distinction rests entirely on the
  message, which is why A requires a negative test.
- **Polling cost.** `/providers/status` also enumerates models and capabilities, so it is not a cheap
  endpoint. A slow interval and a cached read are not optional.
- **The injected token needs a page refresh to rotate**, matching the TTS plugin's accepted trade.

## 8. Decisions

1. **Claude: not now.** It is `enabled: false` in this profile and reports no accounts, so the strip
   covers Antigravity only. Nothing in the design blocks adding it later.
2. **Refresh: pooled, on an assistant response and a one-minute timer**, as set out under B. Meridian
   imposes no client-facing limit and caches at the same cadence, so this adds no load it was not
   already doing for its own dashboard.
3. **Build the host route now, without waiting on Meridian's parser.** The availability state is
   designed as a first-class outcome rather than a temporary condition, so the strip stays useful
   whether or not Meridian ever reads quota for this account again. The connector reports what Meridian
   says, including the reason it cannot say more.

Noted while reading the quota path, and useful for the normalizer in B: Meridian derives
`utilization` as `1 - bucket.remaining_fraction`, sets `type` from the bucket id and groups by
`group.name`, and turns `reset_time` into `resetsAt` with `Date.parse` (`antigravityRuntime.ts:514`).
The failure in §2 happens one line earlier, in schema validation of `reset_time` itself (`:513`).
