## Meridian connector — done, tested, **not live yet**

All of §6/§7 of the plan is implemented in `plugins/dsh-meridian-antigravity/`:

1. **Bug 1 — the content filter on the HTTP path.** Meridian records the block as an
   HTTP **502**, and `meridianError` mapped `>= 500` to retryable `SERVER`, reopening
   the deadlock through the other transport. `meridianError` now reads the body before
   the status, and `meridianErrorFromText` reads the same two conditions out of a
   **non-JSON** body — otherwise a gateway passing the wording through verbatim
   bypassed `detail` entirely. The message is built once by a new
   `contentFiltered(detail, facts)` helper that `streamInterrupted` also calls.
2. **Bug 2 — the spent-batch guard was 2xx-only.** `dispatch` is split into
   `sendMessages` (returns the response at any status; the only place a connect
   failure becomes an error) plus caller-side classification. `accepted` →
   `reachedMeridian`, set the moment a response arrives. `spentIfContinuation` now
   upgrades **any** recoverable failure on a continuation Meridian answered — a cut
   stream, an idle stall, or a non-2xx — and a failure that never reached Meridian
   keeps its retryable code. The idle-expiry throw is routed through it too.
3. **Bug 3 — aborted continuations.** No repair on abort (a cancelled turn is the
   operator's decision), but the dependency is now **tested**: the next request meets
   the spent-batch 409 and the repair answers it.
4. **Dropped agent connections.** `MERIDIAN_AGENT_INTERRUPTED` splits the most frequent
   live failure (22 ledger rows, "subscriber fell behind updates") out of `SERVER`. It
   is retryable exactly as `SERVER` was — a check asserts that, and `isRecoverable`
   learned it or the replay recovery would have stopped being attempted.
5. **The regex was tightened** from `could not be generated` to `model output could not
   be generated`, because the HTTP path feeds whole gateway bodies through it.
6. **Bug 4 — the repair was unreachable in the case it was written for.** Found live at
   20:03 on 10-05 in `session-45365d66` ("Review Active Campaign Log Events"): the
   filter let the model run 62 s, stream a complete 1,250-char refusal, and *then* failed
   the turn. Making the block non-retryable removed the retry that used to deliver
   Meridian's `"already consumed"` 409, which was the repair's only trigger — so the
   transcript stayed on a tool result. The repair now also fires on a `CONTENT_FILTERED`
   failure that has a continuation, and **keeps the delivered text**:
   `MeridianTranslator.closeWith()` closes the streamed block and appends
   `blockedReplyNotice` as a second block. A block on an ordinary turn is still reported.
   `dsh-dd35-preset`'s `isConnectorNotice` was widened to match the marker at the start
   of any line, so a salvaged reply-plus-notice turn stays out of the campaign record.
7. **README** — contract rows, a new statuses-table row for each body-driven 502, the
   *Known limitations* bullet, the test list ("four suites" → five; `serialize-notices`
   was missing).

Every new behaviour was checked by mutating it back out in a throwaway copy; each

## D&D 3.5e — turn 137 recorded a housekeeping note as the DM's reply (plugin fix done)

Found by the user in `session-7003cefe` ("Hello Sophie", 22:27–22:40 on 10-05, the session that also wrote
turns 134–137).

`0137_turn.md` pairs the player's action with this DM output:

> *(OOC: State successfully saved! I've written a detailed snapshot ... to `compaction_save.md` ...)
> Whenever you are ready to answer the pending action...*

The DM's actual reply to that action ("I grin widely, my golden eyes practically flashing in the dim light…",
22:39:26, turn 4 step 2) is in the session and **not** in the transcript.

**Mechanism.** `dsh-context-pressure` injected its notice mid-turn, which opened new steps after the reply:

```
22:38:35 step 1  assistant tool-call, tool-call
22:39:26 step 2  assistant text          <- the real reply
22:39:26 step 3  >>> context-pressure notice injected
22:40:12 step 3  assistant tool-call, tool-call
22:40:28 step 4  assistant text          <- the housekeeping note
```

`memory.js` `captureFrom` takes the **last** assistant message with text in the turn, so the note wins.

**The UI does the same thing, independently.** `latestAnswer()` in
`packages/client/ui-chat/src/client/conversation-nodes/turn-process.ts:117` defines the answer as the
assistant output of the turn's **last step** (`turn.steps.at(-1)`), and everything before that step is
collapsed into the "Took …" process row — which is why the real reply appeared inside that block with the
tool calls, and why `messageCount` counts it. Two implementations, same rule, same failure.

The rule is correct for a genuine player steer ("stop, do this instead"). It is wrong when the mid-turn
message is a plugin notice, because that notice is not a new player request and should not move where the
answer ends.

**Scale.** 282 of 984 recorded turns contain more than one text-bearing assistant message. Inflated by forks
replaying inherited history, so read it as common rather than as a rate.

**Fixed in the plugin**, because touching the harness directly is against the rules of this workspace.
`captureFrom` now anchors on the player's message and reads forward; `replyIndex` stops at the first
work-requesting notice, so text before it is the reply. The guard is that earlier text must exist — a notice
steered during tool work, before the model has said anything, is part of the working phase and its next
message is still the reply. Both orderings are in the corpus; bounding without the guard would have dropped
the genuine replies in the second one. `WORK_REQUESTING_NOTICE_KINDS` lists the kinds (`context-pressure`
today); reporting kinds deliberately do not bound. dd35 tests 51/0, and three mutations each fail the
intended check.

**Still wrong in the browser, by decision.** `latestAnswer()` in the harness projection defines a turn's
answer as its last step, so the UI will keep showing the housekeeping note as the reply and collapsing the
real one into the "Took …" row. Only a harness change would fix that, and harness changes are out of bounds.
The campaign record is now correct; the transcript view is not.

**`compaction_save.md` stays**, by decision: `dm_notes.md` is the general notes file, `compaction_save.md` is
purpose-specific, and the plugin is left alone on that point. So no `message` override was added to the
profile. The campaign's `clock.date` ("3 Years Ago Night" with `time` "Night", so headers read "Night Night")
is also left as is for now.

## Guard coverage + connector conflict repair (complete, needs a restart)

Full plan and amendments: `docs/guard-coverage-and-repair-plan.md`. Restart checklist:
`docs/meridian-spent-batch-plan.md` §9.

**Item 1 — done, needs a restart.** The guard was effective but only inside presets
that mount it: a preset's plugin list is not a Loader row, each preset group
isolates its own `compaction`/`toolResultPruner`, and the shipped `standard`,
`ptc` and `cordis` presets mount the *unguarded* pair. So `plugins/dsh-compaction-guard/cordis.patch.yml`
now also overrides `preset-standard` wholesale, with exactly two rows swapped.
The two swapped names are absolute `file:///` URLs, because the loader anchors a
relative plugin name *only* inside an `insert` list (`anchorInsertedPluginNames`,
`dsh-app-boot`): as first written, `./engine.js` there resolved against the root
entry list's base, failed to import, and would have activated `standard` as
*broken* rather than merely unguarded. `tests/preset-override.test.js` pins the
override to the installed `presets/standard.patch.yml` — same fields, same ids in
order, same isolation, a diff confined to the two swapped rows, and every name a
package specifier or an existing absolute URL. `ptc` and `cordis` remain
unguarded. COST recorded in the patch: the shipped plugin list is restated
verbatim, so upstream changes to `presets/standard.patch.yml` no longer reach
`standard` sessions until it is refreshed. Bundle patches are read at load, so
this needs a **restart**, not just a file save.

**Item 2 — implemented, then narrowed by evidence.** The plan said prefix-signature
drift detection with repair. Signatures turned out to be a weak basis for a
*destructive* repair, because the serialized prefix legitimately changes between a
tool call and its continuation (superseded runtime-context snapshots, notice
filtering), which would risk committing a notice over a genuine reply. Meridian's
own 409 is the authoritative confirmation, so instead `MERIDIAN_CONTINUATION_CONFLICT`
on a continuation takes the repair path with its own notice.

Two follow-ups landed after review:

- **The planned gate widening was withdrawn.** A separate "unresolved batch"
  predicate is the same condition as `analyzeContinuation` returning a diagnosis,
  so it could not change which requests are repaired. All 52 conflicts in the
  session store, across 35 sessions, arrived on a request with trailing tool
  results — a prune replaces a tool result's content, it never removes it
  (`compaction-tool-result-pruner/src/index.ts:165` appends a replacement with
  `surfaceOp: op: 'replace'`). `tests/continuation.test.js` now pins the
  equivalence and the live shapes.
- **The notice no longer asserts one cause.** Meridian's 409 also covers a model
  or execution-control change, so the notice names the possible causes without
  choosing one.

**Item 3 — the request-body capture is in.** `captureRequestBodies` +
`captureDir` + `captureMaxFiles` (50), off by default, one bounded file per
dispatch, written before it is sent, never fatal. Reading `lib/serialize.js` first
answered the open question: a continuation already sends history verbatim because
filtering a superseded `runtime-context` snapshot is itself what moves the prefix,
and there is no existing prefix hash. The per-message signature stays unbuilt until
a capture shows it would help.

**Evidence worth keeping:** turn 8 of `session-0bc7fee5` was accepted on a prefix
identical to the one turns 5–7 were refused on, seven seconds after turn 7, with no
prune in between. Whatever cleared is not understood, which is why §9.2 asks for a
*second* message rather than treating one success as proof.
